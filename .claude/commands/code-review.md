# /code-review — コードレビュー（LUMINA 案件用）

現在のタスクで変更したファイルをレビューしてください。対象は `git diff main...HEAD` と未コミットの変更です。
ファイルが Markdown / JSON / スクリプトだけの場合も、内容の正確さ・整合性をレビューすること。

## レビュー観点（この順で確認）

1. **バグ**：ロジックの誤り、境界値（0 件・空文字・月をまたぐ日付）、非同期処理のエラー握りつぶし
2. **セキュリティ**：API キーや `service_role` の露出、RLS 漏れ、ユーザー入力（スプレッドシート URL・セル値）の未検証、Server Action の認可チェック
3. **型安全性**：`any` の使用、`as` による強制キャスト、`null` / `undefined` の未処理、Zod 等での外部データ検証の有無
4. **命名・構成**：CLAUDE.md の命名規則違反、責務が混ざった関数、`lib/kpi/` に副作用が混入していないか
5. **テスト不足**：KPI 計算やバリデーションにテストが無い、正解値との突き合わせが無い
6. **初心者向け説明**：README・コメントが専門用語を補足しているか

## 出力形式

重要度順に並べ、各指摘に「場所（`ファイル:行`）」「何が問題か」「どう直すか」を書く。

```
## Critical（必ず直す：セキュリティ・データ破壊・明らかなバグ）
## High（マージ前に直す）
## Medium（できれば直す）
## Low（好みの範囲・任意）
## 良かった点
```

- 指摘が無い区分は「なし」と書く。
- 各指摘は初心者にも分かるよう「なぜ問題か」を一言添える。
- 修正はまだ行わず、指摘一覧を出してユーザーの判断を待つ。ユーザーが「反映して」と言ったら Critical → High の順で直す。
